[2] GRID SOLVER vs REAL AWS-WAF TILES — THE INTERESTING ONE
════════════════════════════════════════════════════════════════════════════

  Why this test: the repo is evaluated on REAL photos (fetch_commons.py pulls
  natural images). AWS WAF's "synthetic grid" — the challenge Amazon actually
  serves on signup — is 9 ML-GENERATED adversarial tiles, chosen precisely so
  they are hard. That is a distribution the repo has never been measured on.
  I had a live, captured WAF grid on disk (9 tiles + target word), so I ran the
  repo's solver on it.

  Setup: 9 real WAF tiles composed into a 3x3 with white separator bands
         (matching detect_grid's white=235/min_band=2 expectation).
         Grid detection: ✅ correctly found 3x3 from the separators.

  ── 2a. ZERO-SHOT mode (target="bucket") — OVER-SELECTS ───────────────────
     scores (per tile, row-major):
       tile:  1      2      3      4      5      6      7      8      9
       score: .997   .991   .998   .999   .060   .029   .897   .615  1.000
     → picked [1,2,3,4,7,8,9]  = 7 of 9 tiles   ❌
     truth (GLM read + visual): buckets are 2, 4, 9

     What the scores say: CLIP perfectly separates CLOCKS (0.029/0.060) from
     everything else — but treats EVERY container-ish object as a bucket
     (pot .997, tub/planter .998, bucket .991/.999) and even fires on a hat
     (.897) and a suitcase (.615). The threshold can't save it: the near-misses
     score ABOVE the true positives.

  ── 2b. DISCRIMINATIVE mode (candidates) — BIG IMPROVEMENT ────────────────
     solve_grid(img, "bucket", candidates=["bucket","pot","tub","planter",
                                           "hat","suitcase","clock","bag","cup"])
     scores: [.721 .659 .320 .779 .000 .000 .012 .002 .972]
     → picked [1,2,4,9]  (th 0.5)        — 3 correct + 1 false positive
     → picked [1,4,9]    (th 0.7)        — 2 correct + 1 false positive
     ✅ clocks .000/.000, hat .012, suitcase .002 — all correctly rejected.
     ❌ the pot (tile 1) scores .721 vs the real bucket (tile 2) at .659 —
        the ranking is inverted on the ONE confusing pair.

     This validates the candidates design: it is *the* mode for adversarial
     grids, and it removed 3 of the 4 false positives (hat/suitcase/clocks).

  ── 2c. SAME GRID, CLEAR TARGET (target="clock") — PERFECT ────────────────
     scores: [.000 .001 .000 .000 1.000 1.000 .000 .000 .000]
     → picked [5,6]   ✅ EXACT (tiles 5,6 are the two clocks)
     Flawless 1.000-vs-0.000 separation. So the solver is not "broken on WAF
     tiles" — it is semantically exact when the target is visually distinct.

WHY IT FAILS ON "BUCKET" — and the clean fix
════════════════════════════════════════════════════════════════════════════

  Root cause: domain gap + a genuinely fine semantic boundary.
    • Domain: CLIP was measured on real photographs; WAF tiles are adversarial
      synthetic renders. CLIP's "bucket" concept is broad enough to cover a
      synthetic pot and tub/planter.
    • Boundary: bucket vs pot vs tub is a FINE distinction even for humans,
      and it is exactly the distinction the adversarial generator targets.

  Fix (high leverage, cheap): DOMAIN-ADAPT THE GRID HEAD on WAF-style tiles.
  The head is a small MLP on frozen CLIP features (grid_head.py) — it needs
  labelled tiles, and there is a free, exact label source:

      AWS-WAF problem endpoint → (target word + 9 tiles)      [free, unlimited]
                  ↓
      label with a VLM (GLM-5.3-Flash described these tiles correctly:
            it read pot/bucket/tub/hat/suitcase/clock accurately)
                  ↓
      OPTIONAL: verify each grid against the WAF /verify endpoint
            (server says correct/incorrect → ground truth for free)
                  ↓
      train grid_head on those CLIP features  →  local solver that matches
            the VLM on the synthetic domain, with zero per-call cost

  Expected: the pot-vs-bucket inversion is precisely what a few hundred labelled
  synthetic tiles fixes (the head re-weights the feature space for this domain).
  The clear-target case already works, so the head only has to sharpen the
  boundary, not learn the task.

  Note: do NOT ship a lower threshold as the fix — 2a/2b show the near-misses
  score above the true positives, so no threshold separates them. It must be the
  head (or a better prompt set), not the cut-off.

NOTES / SMALL THINGS
════════════════════════════════════════════════════════════════════════════

• Result extraction is easy to get wrong: text is `Result.text`, grid is
  `Result.selected` — there is no `.value`. README examples show the str()
  repr; add one line to the README stating the field names, or alias
  `.value` → text for ergonomics. (This cost me one full mis-scored run.)
• clip_onnx.py defaults MODEL_DIR to `<repo>/models/clip`, but the models in
  this environment live at `/root/models/clip`. Handled fine via the
  CLIP_ONNX_DIR env var — worth documenting in the README install section
  (fetch_models.py probably writes to one of them; I did not run it).
• detect_grid found the 3x3 from white bands without being told — good, the
  composite I fed it had real separators and it nailed rows/cols.
• discriminative mode is under-sold in the README. On adversarial grids it went
  from 7/9 wrong to 1 false positive. It deserves top billing next to
  "trained head".
